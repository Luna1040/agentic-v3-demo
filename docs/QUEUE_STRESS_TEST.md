# 七轮快速聊天的观测与核对

## 操作

1. 打开要测试的世界，在「世界状态与剧情 → 队列与入库」开始录制下一组七轮。
2. 正常发送消息，每次看到回复保存后立即发送下一条。无需提醒角色记忆，也无需等后台整理。
3. 第七轮后停止发送，等各轮后台状态完成，再导出本组 JSON。

录制只标记观察范围，不改变模型、Prompt、调度速度或世界内容。后台如果始终跟得上，可以没有合批；不能把七轮必然合批当成验收条件。已经在运行的批次不会追加新轮。

## 两种不同的合并

- **WorldOps**：同世界按源回合顺序处理，尚未开始的队列最多三轮合批。同一次模型请求仍须为各轮分别给出结果，再按原顺序原子提交；不会把七段原文覆盖成最后一句。批量语义冲突可拆开逐轮处理。
- **Main**：合并最新的规划需求，不为每次积压的旧请求分别规划。旧执行的结果经过版本和尝试编号检查，不能越过新需求发布。

后台合批节省请求次数，不代表每个角色都知道所有人的信息。各角色的知情范围仍然独立。

## 最终入库怎么算

- 原始玩家消息、已保存的场景回复和 Agent 实际输入输出保留原来源。
- 同一批按原回合顺序应用。后一个来源有证据的**字段修改**更新该字段；未修改字段保留，不用最新一条摘要替换整个世界。
- 约定和移动先区分计划、进行中、完成、取消；提过或者打算做不等于完成。
- 记忆摘要可以更新，但各源回合的记忆快照与原文保留。摘要不是人物、地点、物品和约定的唯一存储。
- 外部版本改变时，旧结果先被记录，再重新基于当前状态整理；不能无条件最后写入覆盖。较旧回合的移动可保留为历史，不能把当前场景拉回。
- 未能应用的候选保留为未归档事项，不作为已经发生的事实，失败也不清除已保存的回复。

这些规则是实现约束，不保证模型没有语义漏提取。用户测试需要同时核对「模型提出了什么」「哪些被接受」「实际数据库变了什么」，不能只看 completed。

## 保存的证据

`world_runtime_audit` 是新增的追加表，记录排队、领取、结果保存、等待前台、版本冲突重算、拆批、失败和实际提交。实际提交包含源回合、版本与修改前后值；与原有 `turns`、`agent_calls`、`world_memory_snapshots`、`world_story_events` 关联。Main 的需求、过期和完成另外记录 lane。

应用数据库角色只有该审计表的 SELECT/INSERT 权限，禁止 UPDATE/DELETE；额外触发器防止常规变更与 TRUNCATE。未配置自动清理。这是应用级可追溯日志，并非数据库管理员也无法修改的外部存证。

API 均需开发权限，并按世界所属用户隔离：

```text
POST /api/worlds/:id/runtime-audit/capture   {"expectedTurns":7}
GET  /api/worlds/:id/runtime-audit
GET  /api/worlds/:id/runtime-audit?captureId=<id>&includeCalls=1
```

普通轮询不请求模型，也不下载完整调用正文。导出时附实际调用输入/输出。数据含聊天隐私，使用当前网站的访问控制；不包含 API 凭据或模型隐藏思考。单次返回最多 2000 个审计事件、500 个调用，超限明确标注，不删除数据库原始日志。

「当前入库快照」带读取时间与世界版本，是读取时的当前状态。继续发第八轮后，它可能包含新变化；判断前七轮应结合各轮的 committed 前后值。录制不会冻结世界。

## 开发验收

`test/seven-turn-backlog.test.ts` 使用真实 PostgreSQL、HTTP/SSE 与生产后台 worker，只控制模型延迟及输出。在第一轮后台被测试门闩阻塞时完成七轮前台，然后观察实际 `[1]、[2,3,4]、[5,6,7]` 合批，核对七轮原文、七次入库、最终字段值与未修改字段保留。门闩仅在测试文件内，正式运行没有人为延迟。

`test/runtime-audit.test.ts` 核对审计的权限、观测范围、冲突、事务与追加记录。受控流程测试不能替代真实模型的语义质量验收；本次七轮由用户在真实环境中完成。
